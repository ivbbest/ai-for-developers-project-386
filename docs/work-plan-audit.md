## 3. Находки и решения

### F1 — Критично для последовательности: 3.5 зависит от мержа этапа 2

Факт: `express.static(frontend/dist)` (шаг 3.5) требует собранный фронт,
который появляется только после мержа `feat/frontend`. Схема
«Порядок и зависимости» рисует этапы 2 и 3 как параллельные ветки с общей
стрелкой в этап 4; зависимость «3.5 ← мерж этапа 2» не зафиксирована.
Это же N10 из `architecture-audit.md` (правка A6 «к внесению»).

Последствия: если `feat/backend-api` дойдёт до 3.5 раньше мержа
`feat/frontend`, шаг встанет; критерий 3.5 («UI и API с одного порта»)
выполним только после этапа 2.

Решение: уточнить в `work-plan.md`: 3.1–3.4 параллельны этапу 2; 3.5 —
зависимая работа, на паузе до мержа этапа 2 (п. F1 → правка F1.1).

### F2 — Корневой `package.json` с workspaces не запланирован

Факт: «Локальный запуск» (`work-plan.md:203-221`) использует
`npm run … -w <пакет>`; структура — монорепо с корневыми workspaces
(§11 решение 3: `contract`, `frontend`, `backend`; `e2e` — отдельная
установка, решение 4). Создание корневого `package.json` не входит ни
в один шаг плана. Это же N11 (`architecture-audit.md`, A7 «к внесению»).

Последствия: после каркаса `contract/` (1.3) команды `-w` из корня
не заработают — потребуется непредусмотренная правка.

Решение: включить создание корневого `package.json`
(`"workspaces": ["contract", "frontend", "backend"]`) в шаг 1.3
(каркас контракта); `e2e` в workspaces **не** включать (решение 4),
включение `e2e` — по решению на шаге 4.1 (п. F2 → правка F2.1).

### F3 — Пересечение пакетов ветками этапов 2 и 3 не зафиксировано

Факт: `feat/frontend` добавляет `contract/mock-server` (пакет этапа 1);
`feat/backend-api` (3.5) трогает `frontend/dist`. Легально (этап 1
мержится раньше), но в диффах выглядит как чужое изменение. Это же N12
(`architecture-audit.md`, A8 «к внесению»).

Решение: зафиксировать в `work-plan.md` «Git-workflow», что ветки этапов 2
и 3 осознанно трогают пакеты смежных этапов (п. F3 → правка F3.1).

### F4 — В `routes.tsp` не запланированы явные `@example` для 404/409

Факт: Prism через `Prefer: code=NNN` отдаёт заготовленный ответ по схеме;
без примера в OpenAPI Prism генерирует динамический пример — smoke 1.6
сработает, но вывод менее детерминирован и читаем. Это же N14
(`architecture-audit.md`, A10 «к внесению», внедрять на шаге 1.5).

Решение: в `routes.tsp` для ответов 404/409 задать явный `@example`
(тело `Error`) — внедрить на шаге 1.5 (п. F4 → правка F4.1).

### F5 — Проверка `better-sqlite3` под Node 24 не в плане

Факт: в `architecture-audit.md` (N8, п. B2) предусмотрена проверка
prebuild'ов `better-sqlite3` под свежий мажор Node на шаге 1.2; в шаге 1.2
`work-plan.md` эта проверка не указана.

Решение: добавить одной строкой в детали/критерий шага 1.2 (запасной
путь: `build-essential` в dev-образе или Node 22 LTS) (п. F5 → правка F5.1).

### F6 — `.agents/tasks.md` «Шаг 1» рассинхронизирован с планом

Факт: список подзадач «Шаг 1» (`.agents/tasks.md:87-98`) не содержит
создания корневого workspaces-пакета (F2) и `@example` для 404/409 (F4).

Решение: синхронизировать список с шагами 1.3/1.5 после внесения правок
в `work-plan.md` (п. F6 → правка F6.1).

### F7 — Статус плана не отражает аудит 2026-09-02

Факт: заголовок `work-plan.md` («Статус») ссылается только на аудит
2026-09-01 (правки A1–A5); находки N10–N14 и план A6–A10 в документе
не отражены.

Решение: обновить строку статуса после внесения правок F1–F5
(п. F7 → правка F7.1).
