## 1. Вердикт

План целостный, контракт продуман; подавляющая часть доменных решений верна
(пересечение интервалов вместо `UNIQUE(start)`, слоты со `status`, MSK-константа,
идемпотентный seed, транзакция). После ревью К1–К7 документы внутренне
непротиворечивы. Однако обнаружено:

- один планировочный дефект, ломающий этап 2: мок Prism **не хранит состояние**,
  критерий «проход сценария против Prism от начала до конца» нереализуем; критерий
  1.6 «все коды из мока» спасается заголовком `Prefer: code=NNN` (N1, уточнено в §7);
- три дыры в контракте, которые на этапе 3 превратятся в расхождения фронта
  и API: 413 и неизвестные `/api/*`-пути не отдают модель `Error` (N2),
  не определено поведение без `?date=` (N3), сущность «владелец» не описана
  моделью (N4);
- одна неверная формулировка в плане тестов: «injectable `now()`» нельзя
  применить к e2e как написано (N5).

## 3. Находки и решения

### N1 — Критично: «сценарий от начала до конца против Prism» нереализуем

Факт (проверено по README Prism): мок-сервер генерирует ответы по схеме OpenAPI,
**не сохраняет состояние между запросами** («Data Persistence» — в официальном
roadmap, не реализовано).

Последствия:
- `POST /api/bookings` → Prism вернёт 201, но `GET /slots` по-прежнему вернёт
  слоты `.status = available` — «забронировал → слот „Занято“» на Prism не проходит;
- созданный `POST /event-types` тип не появится в `GET /event-types`;
- ~~409 недостижим в принципе~~ — уточнение по §7: коды 404/409 **достижимы** через
  `Prefer: code=NNN` (заготовленный ответ по схеме), поэтому критерий 1.6 выполним
  без стаба; нереализуем stateful-сценарий 2.3 «проход от начала до конца».

Решение:
- ввести лёгкий **in-memory стаб контракта** (Express, ~50 строк: 5 ручек,
  пересечения → 409, слоты со статусами, seed `meet-15`/`meet-30`)
  как dev-инструмент этапа 2 (задача 2.1b в `docs/work-plan.md`);
- Prism оставить для smoke по схеме (200/201/400; 404/409 — через `Prefer: code=NNN`)
  и CI-диффа (1.7);
- stateful-сценарий (бронь → «Занято») на этапе 2 — через стаб, на этапе 3 —
  через реальный бэкенд.

### N2 — Модель ошибок противоречит 413 и неизвестным путям

Спека: «все 4xx — только модель `Error { code, message }`». Противоречия:
- **413** (тело > 64 КБ, express limit) — дефолтный ответ Express — HTML, не `Error`;
- **неизвестный `/api/*` путь** — SPA-fallback ловит только не-`/api`, поэтому
  `/api/whatever` вернёт дефолтный Express-404 (HTML).

Решение: расширить коды модели (`payload_too_large` → 413); на бэкенде — единый
JSON-обработчик всех 4xx в формате `Error`. Зафиксировать кейсами E18–E19.

### N3 — Не определено поведение без `?date=`

`date` описан как параметр GET slots, но случай «параметр не передан» не
зафиксирован.

Решение: `date` обязателен, отсутствие → 400 `validation` (E20); в TypeSpec —
required `@query`.

### N4 — Сущность «владелец» не описана моделью

`input/design-first.txt` требует описать доменные сущности: владелец, тип события,
слот, бронирование. В TypeSpec будут только 4 модели; владелец — только в прозе
и админ-ручках. Для формального покрытия шага курса добавить документационную
модель `Owner` (константа профиля, вне API) — 5 минут.
*(Уточнение по §7: в TypeSpec — не «мёртвая» модель, а `@doc`-описание:
модель, не используемая в операциях, не попадает в сгенерированный openapi.yaml.
Реализовано: раздел «Owner» в спеке + правило для шага 1.4.)*

### N5 — «injectable now()» в e2e не работает как написано

Инъекция `now()` — unit-механизм бэкенда; в Playwright (реальный браузер →
реальный сервер) её нет.

Решение: зафиксировать два механизма — unit: injectable `now()`; e2e: env `NOW`
при старте webServer (бэкенд читает) либо динамический расчёт дат в тестах в MSK.
Один механизм оба слоя не покрывает.

### N6 — Требование «отдельно запущенный бэкенд» не валидируется на этапе 2

На этапе 2 бэкенда ещё нет; требование курса «фронт корректно работает
с отдельно запущенным бэкендом» фактически проверяется на этапе 3 (3.5)
и в e2e (этап 4). Зафиксировать это в спеке «Правила реализации», чтобы этап 2
не пытался закрыть несуществующее.

### N7 — Версии и флаги TypeSpec (пред-проверка) — закрыт, ложная тревога

- ~~`--warn-as-error` в официальном help (`tsp --help`) не отображён~~ — проверено
  по исходникам `@typespec/compiler@1.15.0` (§7): флаг **есть**, это опция команды
  `tsp compile` (в верхнеуровневом `tsp --help` не показывается — отсюда ложный вывод).
  Критерии 1.5/1.3 остаются как в плане.
- `tspconfig.yaml` + `output-file-type: yaml` — корректно (эмиттер openapi3
  поддерживает); `contract/dist/` не перекрыт `.gitignore` — подтверждено.

### N8 — better-sqlite3 под Node 24: флаг риска

Нативные prebuild'ы для свежих мажоров Node могут отставать. Запасной путь:
`build-essential` в dev-образе (сборка из исходников) или Node 22 LTS.
Не блокер; пункт проверки на шаге 1.2.

### N9 — Уточнения к критериям этапов (сводно)

Изменения критериев готовности, следующие из N1/N5/N6 (внесены в `docs/work-plan.md`):
- 1.6: Prism smoke по всем кодам 200/201/400/404/409; 404/409 — через `Prefer: code=NNN`
  (заготовленный ответ по схеме; уточнено по §7);
- 2.1b: новая задача — стаб контракта; 2.2/2.3: «против стаба», а не «против Prism
  от начала до конца»;
- 3.5: здесь же закрывается требование «отдельно запущенный бэк» (N6);
- 4.x: механизмы фиксации «сегодня» — по N5 (unit: injectable `now()`;
  e2e: env `NOW` или динамический расчёт).

## 7. Верификация фактов (2026-09-01, по первичным источникам)

- **N7 — закрыт, ложная тревога.** `@typespec/compiler@1.15.0` (npm, исходники):
  опция `warn-as-error` определена для команды `compile` (`dist/src/core/cli/cli.js`,
  `.option("warn-as-error", …)`). В верхнеуровневом `tsp --help` её нет — проверять нужно
  `tsp compile --help`. Критерии 1.3/1.5 в силе.
- **N1 — подтверждён частично.** README Prism: «Data Persistence» — незакрытый пункт
  roadmap (состояния нет — stateful-сценарий на Prism нереализуем, вывод верен).
  Но `@stoplight/prism-http-server@5.15.11` (`getHttpConfigFromRequest.js`) парсит
  заголовок `Prefer` в `{ code, exampleKey, dynamic, seed }`, а negotiator умеет
  подбирать ответ по коду (`findResponseByStatusCode`) — то есть 404/409 из мока
  **достижимы** (`Prefer: code=NNN`, заготовленный ответ по схеме). Критерий 1.6
  выполним без стаба; стаб нужен для сценария 2.3.
- **N4 — уточнён.** Эмиттер `@typespec/openapi3` выводит только схемы, используемые
  операциями: «мёртвая» модель `Owner` в `openapi.yaml` не появится. Фиксация —
  раздел `Owner` в спеке + `@doc` в TypeSpec (реализовано в правках A5).
- **N8 — риск низкий.** Node 24 — LTS; актуальные `better-sqlite3` несут prebuild'ы
  под свежие мажоры. Запасной путь (build-essential / Node 22) оставлен в плане 1.2.

### N10 — Шаг 3.5 зависит от мержа этапа 2 (в схеме зависимостей не отражено)

Факт: `express.static(frontend/dist)` (шаг 3.5) требует собранный фронт, который
появляется только после мержа этапа 2. Схема «Порядок и зависимости» показывает
этапы 2 и 3 как параллельные ветки с общей стрелкой в этап 4; зависимость
«3.5 ← мерж этапа 2» не зафиксирована.

Последствия: если `feat/backend-api` дойдёт до 3.5 раньше мержа `feat/frontend`,
шаг встанет; критерий 3.5 («UI и API с одного порта») выполним только после этапа 2.

Решение: уточнить в `work-plan.md`: 3.1–3.4 параллельны этапу 2; 3.5 — зависимая
работа, ставится на паузу до мержа этапа 2 (п. A6).

### N11 — Корневой `package.json` с workspaces не запланирован

Факт: «Локальный запуск» использует `npm run … -w <пакет>` (флаг workspace),
структура — монорепо с корневыми workspaces (`project-understanding.md` §10/§11),
но создание корневого `package.json` с `"workspaces"` не входит ни в один шаг плана.

Последствия: после каркаса `contract/` (1.3) команды `-w` из корня не заработают —
потребуется непредусмотренная правка.

Решение: включить создание корневого `package.json` (`"workspaces": ["contract",
"frontend", "backend", "e2e"]`) в шаг 1.3 (каркас контракта) (п. A7).
*(Уточнение 2026-09-02: состав workspaces — по §11 решению 3 `project-understanding.md`:
`contract`, `frontend`, `backend`; `e2e/` — отдельная установка (решение 4), команд
`-w e2e` в «Локальном запуске» нет; включение `e2e` в workspaces — по решению
на шаге 4.1.)*

### N12 — Ветки этапов 2 и 3 пересекают границы пакетов

Факт: `feat/frontend` добавляет `contract/mock-server` (плюс зависимость express)
в пакет `contract/` (пакет этапа 1); `feat/backend-api` (3.5) трогает
`frontend/dist`. Это легально — этап 1 мержится раньше этапов 2/3, но в диффах
выглядит как чужое изменение.

Решение: зафиксировать в `work-plan.md` («Git-workflow»), что ветки этапов 2 и 3
осознанно трогают пакеты смежных этапов (стаб в `contract/`, раздача
`frontend/dist`) (п. A8).

### N13 — Опечатка в этом документе

«в верхневном `tsp --help`» (§3 и §7) — правильно «в верхнеуровневом». Исправлено
в обоих местах в этом же обновлении (п. A9).

### N14 — Совет к smoke 1.6: явные `@example` для 404/409

Факт: Prism через `Prefer: code=NNN` отдаёт заготовленный ответ по схеме; без
примера в OpenAPI Prism генерирует динамический пример по схеме — smoke сработает,
но вывод менее детерминирован и читаем.

Решение: в `routes.tsp` для ответов 404/409 задать явный `@example` (тело `Error`) —
детерминированный и читаемый smoke (1.6). Внедрить на шаге 1.5 (п. A10).
