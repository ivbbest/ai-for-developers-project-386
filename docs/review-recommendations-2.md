## P2 — взять в работу первыми

### 1. Бэк превращает клиентские 4xx ошибки Express в 500

- Где: `backend/src/middleware/errors.ts:44–53`.
- Что: хендлер смотрит только на `err.type` (413 и битый JSON). Ошибки,
  которые бросает сам Express с `status=400, expose=true` (например
  `URIError` на некорректный percent-encoding в пути:
  `GET /api/event-types/%E0%A4%A/slots`), проваливаются в generic-ветку —
  клиент получает 500 `server_error`, сервер пишет `Unhandled error` в лог
  на каждый такой запрос.
- Почему: контракт обещает 5xx только для сбоев сервера (E19); мониторинг
  5xx загрязняется мусорным трафиком; поведение расходится с Prism/стабом.
- Проверить: `curl 'localhost:3001/api/event-types/%E0%A4%A/slots?date=2026-09-10'`
  — сейчас 500, должно быть 400 `validation`.
- Починить: перед generic-веткой учитывать `status`/`expose` ошибки Express
  (4xx → 400 `validation` с RU-текстом); регресс-тест в `api.test.ts`.

### 2. Авто-рефреш сетки после 409 молча не работает в dev

- Где: `frontend/src/routes/confirm.tsx:35–38` (флаг) и `:113–116` (рефреш).
- Что: `aliveRef = useRef(true)` инициализируется один раз на инстанс;
  StrictMode (включён в `main.tsx`, на dev-сервере он и живёт) делает
  setup → cleanup (`false`) → setup, но второй setup флаг в `true` не
  поднимает. В dev `aliveRef.current` остаётся `false` навсегда, и `.then`
  рефреша после `slot_conflict` отбрасывает результат. В проде (без двойного
  монтажа) работает; e2e не ловит — тест проверяет только клик по ссылке
  «Обновить слоты», а не авто-рефреш.
- Почему: комментарий обещает поведение, которого нет в конфигурации,
  под которой гоняются e2e; фича фактически не покрыта.
- Проверить: dev, занять слот из второй вкладки, получить 409 — счётчик
  «Свободно» не пересчитается.
- Починить: `aliveRef.current = true` в setup-теле эффекта; либо убрать ref
  (рефреш и так живёт в catch-ветке смонтированного компонента). В e2e —
  добавить ассерт свежей сетки без клика (пересечётся с пунктом 3 ниже).

### 3. «Чистая БД на каждый прогон» e2e не гарантирован

- Где: `e2e/global-setup.ts:6`, `e2e/playwright.config.ts:18–26`.
- Что: комментарий обещает удаление файла БД «до подъёма серверов», но
  webServer в Playwright — плагин, его setup стартует раньше пользовательского
  `globalSetup` (подтверждено чтением `createGlobalSetupTasks` в исходниках
  раннера). Бэкенд уже открыл и насидил `/tmp/cal-e2e.db`; `rmSync` лишь
  unlink'ивает файл у живого процесса — соединения продолжают писать в старый
  inode. В CI скрыто эфемерным /tmp раннера; на хосте повторный прогон
  в тот же /tmp на следующий день видит вчерашние брони и типы: путь гостя
  падает на занятом слоте, «новый тип» — на 409 `duplicate_id`.
- Почему: критерий «чистая БД на прогон» (план, «Тесты/E2E-гигиена»)
  выполняется случайно; локальный прогон по README ломается без ручного
  `rm /tmp/cal-e2e.db`.
- Проверить: два прогона Playwright подряд на машине с переживающим /tmp —
  второй красный.
- Починить: удаление файлов в `pretest`-скрипте `e2e/package.json` (до запуска
  playwright) или в `command` webServer (`rm -f … && npx tsx src/server.ts`).

### 4. Гид по решениям противоречит коду в security-пункте

- Где: `docs/decision-guide.md:296–298` («контейнер работает от root;
  `USER node` отложен») и `:469` («Открыто: 1. `USER node` в образе»).
- Что: с PR #22 в `Dockerfile:28` стоит `USER node`, образ пересобран и
  проверен (запись БД, restart) — пункт «открытых вопросов» описывает
  решённую проблему. Гид противоречит не только коду, но и собственному §8
  и документу первого раунда.
- Почему: главная ценность гида — проверяемость решений фактом; ошибка
  в месте про безопасность подрывает доверие ко всему документу.
- Проверить: `grep -n USER Dockerfile`.
- Починить: переписать абзац (решение принято ревью-прадкой; caveat про
  volume с uid 1000 на Render перенести из README/deploy-гайда), снять
  пункт 1 из «Что осталось открытым».
