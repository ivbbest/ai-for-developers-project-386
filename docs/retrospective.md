# Ретроспектива: что можно было предусмотреть раньше

Дата: 2026-09-01
Контекст: ревью артефактов проектирования (контракт, план, UI-разбор) до начала кода.
Цель — не поиск виноватых, а проверка: какие проверки процесса ловят такие классы
ошибок дешевле, чем их исправление на этапе реализации.

## 1. Найденные расхождения и предотвращающие проверки

| Находка | Как прошла сквозь «зелёный» план | Проверка, которая ловит класс ошибки заранее |
|---|---|---|
| К1: API «только свободные слоты», а UI показывает «Занято» | Спека и UI-разбор существовали рядом, но не сверялись поштучно | **Матрица «экран UI ↔ поле API»**: для каждого элемента каждого экрана — откуда берутся данные; нет источника = дыра контракта |
| К2: «занятость = одно время» вместо пересечения интервалов | Правило было текстом, а не предикатом | **Каждое неформальное правило → формула** (как в математике) + контрпример к наивной реализации |
| К3: спека и план описывали один эндпоинт по-разному (`?date=` vs `?from&to`) | Дублирование описания в двух документах | **Запрет дублей**: план ссылается на спеку, не пересказывает; grep-сверка имён параметров |
| К4: время UTC + «09:00–18:00» + «сегодня» без пояса | Временны́е данные казались «просто строками» | **Чек-лист времени**: любой `date/time` в контракте — пояс, источник «сейчас», DST; иначе не принимать в спеку |
| К5: не зафиксированы тело POST, коды 201, модель ошибок | «Есть эндпоинт» воспринималось как «есть контракт» | **DoR ручки**: request-схема + success-код + все error-коды + схема ошибки — иначе ручка не считается описанной |
| К6: `slug`, `DELETE` без требований | Расширение «на всякий случай» | **Трассировка «требование курса ↔ эндпоинт/поле»**: нет требования — нет в контракте (YAGNI) |
| К7: не решено, кто раздаёт фронт на одном порту | Требования Docker/PORT и «фронт отдельно» читались по отдельности | **Сценарий эксплуатации до кода**: «как это запускается в проде» — один процесс, маршруты, префикс |

Общий вывод: все семь — одного класса «документы внутренне непротиворечивы, но не
сверены между собой и с эксплуатацией». Лечится не призывом «быть внимательнее»,
а тремя артефактами: матрица экран↔API, формулы правил, трассировка требований.
Они введены в спеку/план.

## 2. Крайние случаи

До ревью в спеке не было ни одного явного крайнего случая — были только «счастливые»
правила. Добавлены E1–E17 в `docs/specs/api-contract.md` + правило про занятый порт.
Классы, которые стоило прогонять на каждом контракте заранее:

- **Границы**: стык интервалов (касание ≠ пересечение), первый/последний день окна,
  полночь, «страница протухла», `duration` ровно 540.
- **Повторы и гонки**: двойной клик, две вкладки, параллельные POST, повторный старт
  сервера (seed).
- **Грязный ввод**: формат даты, неизвестные поля, не-JSON, большой тело, unicode.
- **Отсутствующие сущности**: неизвестный typeId на каждой ручке.
- **Инфраструктура**: занятый порт, пустая/утраченная БД, холодный старт площадки.

## 3. Тесты: чего не хватало в первоначальном плане

Изначально «тесты» были одной строкой «юнит-тесты на правила». Неполно: без
перечня кейсов «какое правило — какой тест» слой превращается в smoke. Теперь:
таблица слоёв в `docs/work-plan.md` «Тесты», обязательный регресс-тест на каждый
закрытый баг, injectable `now()` (иначе e2e стареют вместе с календарём), чистая БД
на прогон.

E2E-сценарии сверх основного пути (добавлены в план этапа 4):
1. Два соседних слота разными типами (09:00–09:15 + 09:15–09:30) — оба бронируются.
2. Двойной клик «Подтвердить» — одна бронь, вторая попытка показывает «Занято».
3. Вкладка протухла через полночь — при отправке понятная ошибка + сетка обновилась.
4. Прямая ссылка `/book/unknown` — состояние «не найдено», не падение.
5. Прямая ссылка на дату вне окна — сообщение, а не пустой экран без объяснения.
6. Создать тип «Час» в `/admin/new-type` → появился в каталоге, сетка с шагом 60.
7. Бронь из основного пути видна в `/admin` и отсортирована по времени.

## 4. Дробность задач

Проблема: шаги плана были «размером с фичу» («реализовать слоты»), тест в конце —
ошибку видно далеко от места внесения. Правило (внесено в план):
**задача = одно поведение контракта + его тест + один коммит**. Дробят не по времени
(оценки субъективны), а по признакам: тест на задачу нельзя написать до реализации;
задача трогает несколько слоёв; коммит содержит больше одного логического изменения.

Пример дробления шага 3.2 «Сетка слотов» (было: 1 задача):
- 3.2.1 генерация сетки 30-мин типа в окне дня (тест: 18 слотов, 09:00…17:30) → коммит
- 3.2.2 произвольный duration, граница `end ≤ 18:00` (тест: 540 → 1 слот; 45 → …) → коммит
- 3.2.3 прошедшие слоты сегодня исключены (тест на injectable now) → коммит
- 3.2.4 окно: сегодня…+13, +14 → ошибка (тесты на границы) → коммит
- 3.2.5 статус `booked` по пересечениям (тест: E1, E2-сетка) → коммит

Каждый коммит — зелёные тесты; поиск регрессии (`git bisect`, `git log -L`) работает
только при такой атомарности.

## 5. Коммиты

Честная оценка текущего состояния: история до этого момента — крупные тематические
коммиты «документация + память пачкой», линейная археология («в каком коммите
появилось это решение/строка?») почти невозможна. Что меняется:

- Настоящие правки ревью оформляются **цепочкой логических коммитов** в отдельной
  ветке (правила → спека → план/доки → память), а не одним сваленным коммитом.
- Для кода (этапы 1–5) коммит-чекпоинт на каждое существенное изменение уже
  зафиксировано как правило исполнения; плюс правило «тест в том же коммите,
  что и поведение».
- Сообщения — Conventional Commits, описывают **что и зачем**, без внутренних ссылок.

## 6. Выводы в процесс (зафиксировано в правилах и плане)

1. Матрица «экран ↔ поле API» — обязательный раздел UI-спеки.
2. Правила-предикаты: неформальное правило в спеку не попадает без формулы и контрпримера.
3. DoR эндпоинта: схема тела + коды + модель ошибки; без этого ручка «не описана».
4. Трассировка «требование ↔ артефакт ↔ тест» — в спеке; лишнее не реализуется.
5. Сценарий эксплуатации (порты, процессы, restart) решается до кода.
6. Задача = поведение + тест + коммит; план с задачами крупнее — дробить.
7. Временны́е тесты — только через injectable `now()`.
