## Вердикт

Здоровый, зрелый учебный проект: контракт и реализации совместимы, тесты
не вакуумные, CI покрывает typecheck/build/юнит/e2e, история коммитов читается
как журнал решений. Критических дыр нет. Подавляющее большинство находок —
гигиена CI и отложенные хвосты: **ни одна рекомендация не блокирует текущий
деплой**, все — повышение надёжности и снижение стоимости следующих правок.

## Приоритет 1 — закрыть первым

### Р1. Смержить PR #21 (docs/decision-guide)

`main` не содержит архива `docs/archive/` (work-plan, reading-guide,
specs-TEMPLATE) и `decision-guide.md`, но рабочая документация проекта
(`docs/project-understanding.md`, путеводитель) уже описывает эту структуру
как существующую. Публичный репозиторий выглядит иначе, чем его документация,
а флагманский документ решений недоступен до мержа.
**Почему так:** ревьюировать проект по описанию, которого нет в `main`, — значит
задваивать источники правды; после мержа исчезает класс расхождений «документ
ссылается на несуществующий файл», и рекомендации ниже можно привязывать к
актуальным путям (`docs/archive/work-plan.md`).
**Проверка:** PR #21 открыт, проверки зелёные (hexlet-check и opencode-review),
конфликтов нет — мерж безопасен.

### Р2. Линт фронта не исполняется нигде в CI

`frontend/package.json` объявляет `lint` (oxlint), но ни один workflow его не
вызывает: `e2e.yml` — typecheck/build/unit, `contract-sync.yml` — compile+diff.
Линт-ошибки в PR уходят в `main` без сигнала (пример — глитч форматирования
в `frontend/src/components/ui/select.tsx:72`, который приводит к падению
`prettier --check`, если его кто-то добавит).
**Почему так:** oxlint ловит класс ошибок, невидимый tsc (мёртвый код, небрежное
форматирование, анти-паттерны); без исполнения он — мёртвая строчка в манифесте,
а не защита.
**Как:** одна строка в `e2e.yml` (job `backend-unit`): `npm run lint -w frontend`.

### Р3. Из e2e-плана не покрыты два сценария

`docs/work-plan.md` («Тесты», строка E2E) обещает: «протухшая через полночь
вкладка → ошибка с рефрешем» и «дата вне окна по ссылке → внятное сообщение».
В `e2e/tests/booking.spec.ts` (6 тестов) оба отсутствуют; первый не реализован
и во фронте — `confirm.tsx` выделяет только `slot_conflict`, а
`slot_out_of_window` отдаётся как общая ошибка.
**Почему так:** это не косметика: «ошибка + рефреш» — обещание спецификаций
(крайний случай E3), и единственный способ проверить его — e2e-сценарий;
`slot_out_of_window` — единственное состояние, в котором слот «стал протухшим»
между выбором и подтверждением, и пользователь должен видеть внятный путь
дальше, а не «Слот уже занят».
**Как:** два e2e-теста (env `NOW` на старте webServer уже поддерживается
и используется юнит-тестами; для e2e проще динамический расчёт дат, как в
`mskTomorrow()`), плюс отдельная ветка `slot_out_of_window` в `confirm.tsx`.

### Р4. Контейнер работает от root

`Dockerfile:20-32` (runtime-образ `node:24.20.0-slim`) не объявляет `USER node`,
хотя этот пользователь существует в базовом образе.
**Почему так:** при компрометации Express-процесса атакующий получает полный
контроль над контейнером; с `USER node` — только над приложением. Фикс тривиален,
риск — стандартный пункт большинства чек-листов безопасности контейнеров.
**Проверка:** после правки `docker run` с healthcheck и записью в volume
`backend/data` (права на запись у `node` должны быть).

### Р5. При смене типа события остаётся старая сетка слотов

`frontend/src/routes/book-slot.tsx:40-75`: эффект загрузки типа не сбрасывает
`day`/`slots`/`selected`; react-router переиспользует компонент при смене
`:typeId` в адресе (`/book/meet-15` → `/book/meet-30`), поэтому под новым
заголовком продолжает показываться сетка и выбор предыдущего типа.
**Почему так:** пользователь, перешедший по ссылке с другого типа, видит
данные чужого типа и может подтвердить не то; это самый заметный сценарий
«неверный UI-стейт» из найденных во фронте.
**Как:** сбрасывать стейт при смене `typeId` (вложенный компонент с `key={`${typeId}`}`
или deps в эффекте).

### Р6. API-клиент без таймаута и отмены

`frontend/src/api/client.ts:14-26`: запросы без `AbortSignal`/`timeout`; зависший
бэкенд оставляет все экраны в бесконечном skeleton, а seq-гард
в `book-slot.tsx:64` не сработает, потому что ответа не будет вовсе.
**Почему так:** сеть не гарантирует завершения; без таймаута деградация сервиса
превращается в «зависший» интерфейс без вариантов действий.
**Как:** `AbortSignal.timeout(...)`, отмена при размонтировании, общий
обработчик таймаута в одном месте клиента.

## Приоритет 2 — починить при ближайшей возможности

### Р7. Контрактная проверка ответов бэкенда не исполняется в CI

`contract-sync.yml` сверяет только скомпилированный `openapi.yaml` с
коммиченным (diff). Реальная защита — `backend/scripts/contract-check.sh`
(prism-proxy: ответы живого бэкенда валидируются по OpenAPI) и smoke-скрипты
контракта (`contract/smoke.sh`, `contract/mock-server/smoke.sh`) — нигде
автоматически не запускаются.
**Почему так:** дрейф реализации от спеки ловит только живая сверка ответов;
сейчас она — ручной шаг, который легко забыть, а это единственный механизм
проекта, держащий бэкенд в узде контракта.
**Как:** шаг в `e2e.yml`: поднять бэкенд, прогнать `contract-check.sh` (или
повторить его логику в workflow).

### Р8. Стаб контракта расходится с бэкендом в двух кодах ошибок

`contract/mock-server/server.js:126-128` возвращает 400 `validation` для
прошедшего `start`, тогда как контракт (E3) и бэкенд — 400 `slot_out_of_window`;
`server.js:67-69` дает 400 `validation` на нечисловой `{id}`, бэкенд — 404
`not_found` (`backend/src/routes/eventTypes.ts:18-22`).
**Почему так:** стаб по плану — «вторичный источник правды, сверяется
с контрактом»; пока он расходится, фронт в dev-режиме и прод-режиме показывает
разные сообщения об ошибках, и будущие инструменты увидят «движущуюся мишень».
**Как:** привести стаб к поведению бэкенда.
**Сверка 2026-09-03: подтверждено, исправлено в этой ветке** — прошедший
`start` теперь отвечает `slot_out_of_window`/«время слота уже прошло»,
несуществующий id в слотах — 404 `not_found` (как бэкенд, который проверяет
наличие типа раньше формата id); смоук стаба обновлён.

### Р9. Плавающий node:24 в CI против пина 24.20.0 в Dockerfile

Dockerfile зафиксировал `node:24.20.0` именно из-за дрейфа версий (комментарий
в `Dockerfile:4-5`: локально было 24.20.0, в CI — 24.18.1), но `e2e.yml:45,61`,
`contract-sync.yml:40`, `docker-compose.dev.yml` продолжают использовать
плавающий `node:24`.
**Почему так:** выбор «одна среда везде» уже объявлен в комментариях
`e2e.yml:8-9`; плавающий тег в CI воспроизводит ту самую проблему, ради
которой пин появился, — ошибки, невоспроизводимые локально.
**Как:** заменить `node:24` → `node:24.20.0` в четырёх местах.

### Р10. env NOW — тихий выстрел в проде

`backend/src/services/now.ts` — плановый механизм фиксации времени (работает
для unit и e2e), но в продакшен-документации (`docs/deploy-global.md`) не
упомянут: случайно выставленный `NOW` молча «заморозит» календарь (слоты,
469-фильтр `start >= now`), без единой записи в лог.
**Почему так:** механизм тестирования не должен молча действовать в проде;
диагностика «нет слотов» при живом сервисе — худший класс инцидентов.
**Как:** строка в `deploy-global.md` («не задавать NOW в проде») + строка в лог
при старте, если `NOW` установлен.

### Р11. Гонка «проверка → вставка» закрыта только для одного процесса

`backend/src/repositories/bookings.ts:82-98`: чек пересечений и вставка — в
одной транзакции better-sqlite3; для одного синхронного процесса этого
достаточно, но WAL включён (приглашение к нескольким процессам), а уникального
индекса `(event_type_id, start)` нет — два инстанса могут вставить дубли.
**Почему так:** комментарий в коде честно декларирует однопроцессность; чтобы
инвариант «слот занят = одна бронь» держала СУБД, а не дисциплина, нужен
backstop, либо однопроцессность должна быть зафиксирована явно.
**Как:** `UNIQUE (event_type_id, start)` + регресс-тест, либо запись
«однопроцессный сервис» в архитектурную секцию decision-guide. По факту
одного процесса — низкий риск.

### Р12. Prod-образ не собирается в CI, деплой ручной

`e2e.yml` гоняет `vite dev`, а не прод-сборку; `docker build` Dockerfile нигде
не исполняется; README (`README.md:13`) ссылается на Render, но ни
workflow, ни `render.yaml` в репозитории нет.
**Почему так:** сломанный прод-образ (сборка, healthcheck, prune) пройдёт
все зелёные проверки; деплой воспроизводим только владельцем вручную.
**Как:** workflow `docker build` на push в `main` (без публикации) +,
опционально, `render.yaml` с Docker-деплоем.

### Р13. Доступность формы подтверждения

`frontend/src/routes/confirm.tsx:149-169`: поля Имя/Email/Заметки — только
placeholder, без `<label>`/`aria-label` (в `admin-new-type.tsx` корректные
label — стиль внутри проекта непоследователен); ошибки — в `<p>` без
`role="alert"`; календарь (`calendar.tsx`) без русских label для навигации
на странице `lang="ru"`.
**Почему так:** скринридер не озвучивает поля формы; поздние async-ошибки
не анонсируются; это автоматически отсекает часть пользователей.
**Как:** label (скрытый или видимый), `role="alert"` на блоках ошибок,
`labels`-пропсы реакт-day-picker.

### Р14. Ручные зеркала типов дрейфуют от контракта

`frontend/src/api/types.ts:46-52` не содержит кода `server_error`, который есть
в `contract/dist/openapi.yaml` (реальные 500 маппятся в `'unknown'` — сообщение
показывается, так что impact ограничен); `contract/models.tsp:34-36` не
ограничивает длину email, а бэкенд — `.max(254)`, т. е. сервер отклоняет
валидные по контракту длины.
**Почему так:** типы не генерируются (осознанное решение), значит дрейф —
вопрос времени; у бэкенда есть prism-сверка, у фронта — ничего.
**Как:** минимально — CI-напоминание (diff-проверка frontend-типов против
openapi), либо кодогенерация; расхождение по длине email — решить в одну
сторону (поправить tsp или убрать max в zod-схеме).
**Сверка 2026-09-03: подтверждено** — `server_error` действительно отсутствовал
в клиентском union (коммит «contract fix» обновлял union молча промахнувшимся
replace — урок про assert при replace записан в learnings); исправлено в этой
ветке. Расхождение по длине email — открыто, требует решения владельца.

## Приоритет 3 — гигиена и полировка

- **e2e-хардкод**: `booking.spec.ts:41,109-110` — захардкоженные
  `09:45 - 10:00` и пересчёт `dayMinutes` дублируют константы бэкенда;
  смена формата времени сломает suite. Вынести в один параметр/утилиту.
- **Fixed sleep в e2e**: `booking.spec.ts:132-135` — `setTimeout(800)` в
  `page.route` ради проверки disabled-кнопки; тормозит suite (задержка
  применяется и к последующему админ-запросу) и будет флакать на медленных
  раннерах. Заменить на детерминированное ожидание состояния.
- **Разнобой версий checkout**: `opencode*.yml` — `actions/checkout@v6`,
  остальные — `@v7`; третьи стороны плавают по major-тегам (кроме
  открытого кода opencode.yml, где SHA-пин). Унифицировать и рассмотреть
  SHA-пины.
- **Нет `timeout-minutes`** у opencode-джобов (дефолт — 6 часов на раннере).
- **Нет `actions/cache`** — каждый прогон e2e/contract-sync — холодный
  `npm ci` + установка Chromium.
- **release-please-config.json:4-5**: `bump-minor-pre-major` и
  `bump-patch-for-minor-pre-major` — не «гасят» друг друга, а комбинируются
  (первый: breaking→minor, feat→patch до 1.0; второй возвращает feat→minor).
  После 1.0.0 оба неактивны — удалить или оставить как настройку «на нулевую
  эпоху» на усмотрение.
- **CORS**: отсутствует намеренно (SPA и API — один порт). Черновая формулировка
  про «dev-связка без CORS не работает» — ложная тревога, снята сверкой: dev-связка
  идёт через Vite-proxy (тот же origin), CORS не нужен и там.
- **Мёртвый код**: неиспользуемая ветка `INSERT_SQL` с `ignore: false`
  (`backend/src/repositories/eventTypes.ts:38-49`); ~1 300 строк
  неиспользуемых shadcn-компонентов (`sidebar.tsx` и др., tree-shaken из
  бандла, но раздувают репозиторий).
- **`backend/dist/` на диске устарел** (сборка 2 сен, `src/` правился 3 сен);
  git-ignored, но может запутать — пересобрать или удалить.
- **`endIso` fallback во фронте** (`confirm.tsx:85-87`) дублирует серверный
  расчёт `end` — риск расхождения в отображении (low, только при отсутствии
  `?end=` в URL).
- **Дрейфы чисел в документах** (частично снято сверкой): `decision-guide.md` —
  «шесть экранов» при семи маршрутах (not-found добавлен позже) — свести к
  единому счёту; «vitest 64» против «63 it» — не расхождение: цикл TZ-тестов
  даёт два теста из одного блока (63+1=64), снять претензию; «4/4» (шаг 4.1)
  против «6/6» (шаг 4.2) — корректные снимки разных дат, не противоречие.
- **`docs/deploy-global.md`**: нет сценария отката (rollback) и перечня
  операторских переменных окружения (`DATABASE_PATH`, `STATIC_DIR`, `NOW`).
- **README не даёт поднять полный стек**: dev-связка «бэкенд :3001 +
  фронт :5173» описана только в `decision-guide.md` §5.2; в README — лишь
  прод-режим. Стоит добавить одну секцию «Запуск в dev».

## Осознанные ограничения (не чинить)

Эти решения — намеренные, рекомендации не требуют. Перечислены, чтобы
ревью не создавало ложной тревоги:

- **Отсутствие rate-limiting и авторизации** у админ-ручек — ограничение
  учебного задания.
- **Плавающий `hexlet/project-action@release`** — файл курса, менять нельзя
  (триггер на все ветки и теги даёт лишние прогоны, но это плата за курс).
- **Типы фронта — ручное зеркало** контракта, генерация отложена.
- **`before_pull`-семантика 409/стыков**: строгие `<`/`>` в пересечении —
  по спеке (касание не конфликт).

## Предлагаемый порядок работ (после сверки)

1. Смержить PR #21 (Р1) — устраняет класс «документ ссылается на отсутствующее».
2. Один PR «CI-гигиена»: Р2 (lint), Р7 (contract-check в CI), Р9 (пин node),
   P12 (docker build).
3. Один PR «e2e-доводка»: Р3 (два сценария), гигиена sleep/хардкода.
4. Отдельно: Р4 (USER node), Р5–Р6 (фронт-стейт и таймауты), Р10 (NOW),
   Р13–Р14 (доступность и типы).
5. Низкий приоритет — по остаточному принципу, инициативами владельца.

Каждый пункт — по циклу проекта: ветка → коммиты → PR → зелёные проверки.
