## Как ревьюить ветку/PR (что сделано на этапе)

Идти по коммитам, а не по файлам — каждое изменение = один логический шаг.

```bash
git log --oneline main^..BRANCH        # список атомарных коммитов ветки
git show <SHA>                          # что и зачем в конкретном коммите
git diff --stat main..BRANCH            # итог: задетые файлы
git grep -n <паттерн> main..BRANCH      # поиск рассогласований по всей ветке
```

Проверка одного коммита: (1) сообщение — Conventional, без ИИ-слов и внутренних ссылок;
(2) `git show --stat` — только ожидаемые файлы, без секретов/PII/мусора; (3) диф
соответствует заявленному шагу. Для ветки целиком: зелёные проверки и отсутствие
противоречий между документами (см. цикл ниже).

## Цикл исполнения задачи (один виток = один шаг плана)

1. **Взять шаг** из `docs/work-plan.md` (например 1.4 `models.tsp`) → открыть его ссылку
   на деталь (спека/§9) — там всё для реализации, додумывать не нужно.
2. **Реализовать** минимально по спеке, в ветке текущего этапа.
3. **Проверить фактическим результатом**: выполнить критерий готовности шага (compile/build/тест/curl)
   и увидеть зелёный вывод, а не «должно работать».
4. **Прогнать тесты слоя** (work-plan «Тесты») — без них шаг не закрыт.
5. **Коммит-чекпоинт**: перед ним `git diff` — без секретов/PII/чужих правок.
6. **Отметить шаг** `[x]` в `docs/work-plan.md` и чек-листе; крупное решение — в память.
7. Следующий шаг; смена этапа — новая ветка (и мерж предыдущей).

Правила остановки: задача дробится не «по времени», а по атомарности — одно
поведение контракта + его тест + один коммит; если тест на задачу нельзя написать
до реализации или задача трогает несколько слоёв — она крупная (work-plan
«Дробность задач»); найдено противоречие — править источник правды (спеку/§11),
а не обходить молча.
