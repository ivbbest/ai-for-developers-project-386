## Секреты и `.env` (НЕ читать)

- `.env` и секреты (API-ключи, пароли, токены) — **вне контекста**, считать
  несуществующими. Смотреть/менять/создавать может только пользователь; агент — никогда.
- **Запрещено**: читать/подставлять/выводить/логировать значения секретов,
  писать их в файлы, коммиты, задачи, issues/PR.
- Допустимо знать только *имена* переменных (например `ANTHROPIC_API_KEY`);
  значения — никогда. Ключи в GitHub Actions secrets добавляет только пользователь.

## Границы действий

> **Git-workflow (решение пользователя 2026-09-01).** Каждая существенная разработка —
> **отдельная ветка от `main`** с именем `<тип>/<тема>` (`feat/api-contract`,
> `feat/frontend`, `feat/backend-db`, `test/e2e`, `ci/release`, `docs/...`,
> `build/docker`). Агент создаёт ветки, **коммитит в них** (чекпоинт на каждое
> существенное изменение). **Push ветки и открытие PR — пользователь** (в текущем
> окружении push агенту закрыт правилами). **Слияние в `main`, пуш
> в `main`, force-операции, удаление веток — только пользователь.**

- **Зависимость работ**: новая разработка, опирающаяся на неслитую ветку, — на паузе
  до мержа зависимости в `main`. Независимые работы (например фронт и бэк после
  мержа контракта) — параллельные ветки и PR.
- **Перед каждым коммитом — перепроверка**: прогнать доступные проверки (build/тесты/
  компиляцию контракта), посмотреть `git diff` (что попадает — без секретов, PII,
  мусора и чужих изменений); один коммит = один логический шаг.
- **Тесты обязательны**: изменение без тестов соответствующего слоя не считается
  законченным; слои тестов и где они запускаются — `docs/work-plan.md` «Тесты».
- `git clone`/`fetch`/`status`/`diff`/`log` (чтение) — можно всегда.
- **В сообщениях коммитов, PR, коде и product-документации — без формулировок
  «в стиле ИИ»** («AI», «ИИ» и подобное) **и без ссылок на `AGENTS.md`, `.agents/`** —
  это внутренняя инфраструктура; наружу (диффы, история, README приложения) не тащить.
  Исключение — учебные planning-доки курса (`docs/project-understanding.md`,
  `docs/reading-guide.md`, `input/`): предмет курса — разработка с агентом.
- **Формат сообщений коммитов — Conventional Commits** (`feat:`, `fix:`, `docs:`, `ci:`,
  `refactor:`, `test:`): агент пишет коммиты в этом формате (нужно для release-please,
  шаг 4 курса).
- `hexlet-check.yml` — не менять (удаление/правка ломает автотесты курса).
- Дополнительные workflow (`opencode*.yml`, `e2e.yml`, `release-please.yml`) создаются
  только по явному запросу пользователя; состав и назначение — `.github/workflows/`
  (см. runbook в `.agents/mem/github-integration.md`).

## Память сессии

- **Журнал «Что сделано»** — `.agents/context.md`: записи «дата + факт + SHA» (1–2 строки).
- **Индекс фактов** — `.agents/mem/MEMORY.md`: 1 строка на запись, категории
  `user`/`feedback`/`project`/`reference`; детали — топиками рядом.
- **Извлечённые уроки** — `.agents/mem/learnings.md`: append-only, добавлять
  только в конец; обязательный ритуал конца сессии (см. `.agents/tasks.md`).
- **Коррекции пользователя** записывать **в моменте**, только добавление
  (append-only), формат `YYYY-MM-DD | правило | источник`.
- **При старте задачи** — читать `MEMORY.md` (индекс) и актуальные топики;
  в конце — чек-лист закрытия: обновить `context.md`, `MEMORY.md`,
  `mem/learnings.md`, `.agents/tasks.md`, показать список обновлённого.

## Контекстная гигиена (экономия токенов)

- Большие файлы: сначала Grep/точечные выборки, потом Read с offset/limit;
  результат уже в контексте — не перечитывать.
- Тяжёлый ресёрч/ревью (>3 файлов, объёмные чтения) — субагентом (explore/general).

  не больше ~1500 токенов; описание-триггер — одно предложение с ключевыми словами.

## Принципы работы

- **Верифицируй работу, а не декларируй.** После правки — фактический результат
  проверок (вывод/exit-code), а не «сделано».
- **Пойми последствия до правки (impact analysis).** Найди все затронутые места
  (grep), оцени риск; неясно — сначала исследование.
- **Ревью диффа перед сдачей.** Ветки с логикой (>3 файлов) просматривать свежим
  контекстом (субагент читает diff и критерии); микро-правки — без ревью.
- **Исправляй причину, а не следствие.** Не подавляй исключения и не ставь
  таймауты наугад; корень вне зоны — тикет + ссылка в коде.
- **Комментируй причины, а не факты** (why-comments): «почему», не «что».
- **Игнорируй чужие изменения.** Правки, которые не делал, считай осознанными;
  в чужие файлы — только по явной просьбе.
- **Переиспользуй, не дублируй.** Если есть готовое (эталон, шаблон, функция) —
  используй его, а не копируй.
- **Чекпоинты при многошаговых правках.** Шагами: фиксация → проверка → зелёный
  (коммит-чекпоинт в рабочую ветку) → красный (откат `git restore`).
